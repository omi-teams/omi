---
name: omi-task
description: Run one OMI task end to end - worktree, engineer in the Docker worker, review, PR, CI, merge into development.
argument-hint: TASK-NNN
---
Task: $ARGUMENTS. If empty, take the `next` task from `python -m omi status`.
Several IDs (`omi-task <ID> <ID>`) only when the PO asks: run `python -m omi parallel <IDs>` first and stop with its output on a conflict; then run each task's steps, engineers with `omi dispatch`, no PO accept question per task.

The main checkout stays on `development`. `<wt>` is `../<repo-name>.wt/<ID>`.

0. Before starting or resuming, follow the task-start tool choice below and record the tool, model alias and effort; no PO question.
1. Check that every `depends` task is done and that the task's `role` (a file in `.omi/agents`) and `skills` (chosen from `.omi/skills/CATALOG.md`, regenerate with `python -m omi skills`) pass `python -m omi skills check <task-file>` (role default skills count too). Set `status: in-progress`, then commit on `development`. With a remote, push `development` right away (`git push`), so the squash merge of the PR does not conflict with an unpushed local commit.
2. If `<wt>` already exists, this is a resume (also in a new Claude Code or Codex session; Codex: follow this file for the ID): read its Checkpoint and `## Reports` and verify it with `git -C <wt> status` and `git -C <wt> log development..HEAD`. Otherwise run `git worktree add <wt> -b task/<ID> development`.
   Check `type:`, `parent:` and `workflow:` against `omi-skill-issue-types` (`omi step` warns on a type/workflow mismatch). Drive the task through its `workflow:` (none set: pick the lightest fitting one from `.omi/workflows/CATALOG.md` and write it; default `omi-flow-feature`) with `python -m omi step <ID> next` before and `done` after each step (it commits the task file itself; `WARN: scope touches ...` suggests `omi-flow-feature-sensitive`); `omi run` loads the current step's skills. `coordinator` steps are yours (the `pins` step of `omi-flow-feature-sensitive`: when the scope has `.github`, resolve every `uses:` tag with `gh api repos/<owner>/<repo>/releases/latest --jq .tag_name` and `gh api repos/<owner>/<repo>/commits/<tag> --jq .sha` and record `Pin: <owner/repo>@<tag> <sha>` under `## Checkpoint`; `dispatch next` waits for it); an `auto` gate (accept after review PASS) needs no approval, `done` records `Auto accept: review PASS`; before `done` on a `po` gate, run `python -m omi step <ID> approve --why "<PO's words>"` to record the approval in `## Steps`.
3. Run the engineer in the Docker worker (never spawn an `omi-agent-engineer` subagent, never run it on the host):
   `python -m omi dispatch <role> <ID>`, then `python -m omi watch --wait` (`watch <ID>` for one task; each session has its own read cursor; detached run records survive the session; `omi watch --all` shows history). For explicit per-run overrides use `python -m omi run <role> <ID> [--model M --effort E]` (role from the task, default `omi-agent-engineer`; add `--tool codex|claude` to override the `tool:` of task or role; when an agent hits its usage limit `omi run` switches to the other tool itself and records it in `## Checkpoint`, exit 5 with a `QUOTA:` line means both are out: tell the PO and stop, nothing is lost). Pass `--model/--effort` only when the AGENTS.md quota rules differ from `.omi/agents/<role>.md`. It prints the engineer's report.
   On a fix round `omi run` resumes the engineer's previous CLI session (same tool; `Session: <tool> <id> <role>` under `## Checkpoint`, transcripts in a per-task Docker volume, never on the host, removed by `omi clean`; a token found in it drops the session) with a short prompt pointing at the new findings; `--fresh` starts a new session, a tool switch starts fresh, a lost session prints `RESUME FAILED:` and starts fresh; read roles never resume. If the `post-run` hook fails, the engineer is resumed once with the hook's output tail to fix it and the hook reruns. So write fix-round findings under `## Checkpoint` and keep that `Session:` line.
   If it stops because Docker is not running or no token is found, tell the PO (token: `python -m omi token set`) and stop. There is no host fallback.
   Use the loop, not single commands: `omi dispatch` / `omi dispatch next` start `omi drive` (one detached loop per project; `auto_drive: false` in `.omi/config.json` turns it off), which runs `omi advance` for every finished run whose next action is `NEXT:` and `omi dispatch next` when a slot frees (`auto_dispatch_max` in `.omi/config.json`, default 1, 0 = off); `omi advance` also runs `dispatch next` after a merge. While the driver runs you handle only `DECIDE:` lines (see `omi watch`, `.git/omi-runs/drive.log`); for an unattended squad run `python -m omi drive --loop` (`omi drive --install` registers it as a Windows scheduled task, POSIX prints a cron line; `--uninstall` removes it) (keeps running idle, resumes an in-progress task after your `omi note` before planned ones, stops a task only on DECIDE, QUOTA or ROUND LIMIT). One Coordinator session per task: `advance`, `step` and `dispatch` refuse while another live session holds the task lock. Stop a run with `python -m omi stop <ID>` (watch: `DECIDE: STOPPED by <who>`, never resumed); `run_timeout` in `.omi/config.json` (default 2 h write, 1 h read) ends a run with `DECIDE: TIMEOUT`, a revoked login with `DECIDE: AUTH: <tool> login invalid; run <login command> on the host`. After you fix a failed post-run hook on the host and commit, `python -m omi advance <ID> --hook-fixed` accepts the write step once `omi hook post-run` passes, without a new run. Never run package managers (npm, pip, go mod) on the Windows host inside a worktree: they write host binaries the Linux worker cannot use; do not type `advance` or `dispatch next` by hand for a `NEXT:` line unless the loop is off. `dispatch next` skips a task with no skills picked: set `skills:` first.
4. Check the diff before advancing: `git -C <wt> status` and `git -C <wt> diff`. On write-role DONE, `omi watch` prints `NEXT: python -m omi advance <ID>`. Run that command: it checks the authoritative scope (including committed paths and exact entries for every `.git*` path), uses git to commit on the host with the report's Suggested commit, rebases on `development` (aborts conflicts), pushes and opens a draft PR for a GitHub remote, then runs `python -m omi host-test <ID>`. Without a GitHub remote it skips push/PR. If the suggested message is missing or invalid, pass `--message "<msg>"` with a one-line conventional commit message.
   Each stage prints one line and stops on its first failure; nothing outside scope is committed or reverted. Fix the cause and rerun advance; completed stages are skipped. A changed HEAD needs a fresh DONE write run. `HOST TEST FAILED` records a fix round; record the findings and rerun the engineer before review. On success advance runs `omi step <ID> done`, `next` and `omi dispatch` for the next reviewer, including the security reviewer when the next step is security. Use `omi watch --wait` to collect the reviewer result. After a reviewer FAIL below the round limit `omi watch` prints `NEXT: python -m omi advance <ID>`: it copies the finding lines under `Review round N FAIL:` in Checkpoint, runs `omi step <ID> back`, sets the PR back to draft (skipped without a GitHub remote) and dispatches the engineer (the architect after REPLAN); read the findings first and pass `--reject <n>[,<n>] --why "<reason>"` to leave out a wrong one (recorded as `Coordinator rejected finding <n>: <reason>`); when all are rejected it stops and you decide (`omi step done --po` or fix). `ROUND LIMIT` stops it for your decision. Keep `omi run` / `omi host-test` available for direct runs and fix rounds.
5. Handle the engineer's result:
   - `DONE`: use `python -m omi advance <ID>` after the diff check (step 4); it starts the workflow's next reviewer via `omi dispatch` (fresh instance in a read-only container; it first runs tests, scope and skills checks and, if one fails, reports it instead of starting: treat that as a fix round; skip it only by the path rule in AGENTS.md "Quota rules").
   - Review `FAIL`: run `python -m omi step <ID> back`, write the findings under `## Checkpoint` in `<wt>`'s task file after a line `Review round <N> FAIL:`, commit, and run step 3 again. `omi step back` and `omi run` enforce `max_fix_rounds` (2): at the limit they print `ROUND LIMIT: <ID> failed <N> review rounds; the Coordinator decides` and exit non-zero. You decide (rescope, replan, or one more round): for one more round pass your reason as `--why "<reason>"` to `back` or `omi run`; it is recorded as `Coordinator round override N: <reason>`. Do not ask the PO. When the report ends `ROOT: same` (from round 2) `back` goes to the architect step and prints `REPLAN: same root cause`; run the architect, then build again. A workflow without an architect step needs `--why "<reason>"`.
   - `NEEDS SCOPE`: if it fits the task goal, widen `scope` in the task file on `development` and commit it there (`omi run` copies the new scope into the worktree copy, `SCOPE SYNCED:`), and rerun. Otherwise the Coordinator files a new task (or asks `omi-agent-architect` on a design question); only extra operating cost goes to the PO.
   - `FOUND: <one line>` (from any report, review or your own check): before any other step, file every finding about omi itself with `omi improve "<one line>" --kind bug --from <project>` (`--kind security` for security, `--kind idea` for ideas), setting `OMI_TASK=<source-task>` and `OMI_AGENT=<reporting-agent>` so provenance is preserved. With no omi project registered, retain the printed issue text and command for the user to run. Project bugs stay in the project: write a new task file for it (type, parent, workflow and body by `omi-skill-issue-types`), commit it on `development` and push (`git push` with a remote). No PO question; run it after the current task (step 8).
6. On review PASS, `omi watch` prints `NEXT: python -m omi advance <ID>`. Run it: when another reviewer follows, advance closes the review, starts and dispatches that reviewer, then stops. After the final review it requires every criterion to be marked ✓ with matching criterion text. For every reported `HOST` check, run it and record `Host: <command> [host|container|ci] -> PASS|FAIL` under `## Checkpoint` (the command, where it ran, the result); a line without a command or environment, a missing or a failed line stops advance before changes. No merge without one passing `Host:` line per `HOST` item; a reviewer `HOST: none` needs none. Reviewer commands are never executed by advance.
   Advance ticks the criteria, sets status done, completes review and the final `auto` accept gate, then runs `omi hook pre-merge <ID>` (non-zero blocks). With a GitHub remote it commits acceptance, pushes, writes the body to a file with Verification from Usage rows, Host lines and Steps/Reports, calls `gh pr edit task/<ID> --body-file <file>`, and `gh pr ready`. It runs `gh pr checks --watch --fail-fast`, then a final `gh pr checks` immediately before merge. Either failure runs `omi step <ID> reopen --why "CI failed: <check names>"` and stops without merging; fix and obtain a fresh review. For direct CI recovery use `omi step <ID> reopen --why "<CI failure reason>"`, then complete review and accept again. Exit 0 permits `gh pr merge --squash --delete-branch --subject "<PR title>"`, then `git pull` on development. Without a GitHub remote it runs `git merge --squash task/<ID>` and commits with the title. Each stage stops on failure; rerunning skips completed stages.
   - Title: `[TASK-NNN] <type>(<area>): <summary>`; type is one of feat, fix, docs, chore, refactor, test, ci; English, imperative, at most 72 characters.
   - Body sections, in order: `## Summary` (1-2 lines, plan and task id), `## Changes` (per file or area), `## Not in this PR`, `## Verification` (test command -> result, review rounds and verdicts, security review when the workflow has one, one `Host:` line per HOST check), `## Known issues` (or `none`).
   - PR comments: open the PR as a draft right after the first build commit is pushed (`gh pr create --draft --base development --head task/<ID> --title "<title>" --body-file <file>`, the Verification section is filled in at step 6); mark it ready (`gh pr ready`) once every review-type step of the workflow (review, security, any other `gate review`) has passed; a later FAIL or `step back` turns it back into a draft (`gh pr ready --undo`). While a PR for `task/<ID>` exists, `omi run` posts each final report and hook result as a comment itself. You post Coordinator decisions (scope widened, step back, fix round, `Host:` checks) and PO approvals (quote the PO's words) by writing the header and text to a file and running `gh pr comment task/<ID> --body-file <file>` (never `--body` with `\n`); the header is `**Step:** <step> · **Agent:** Coordinator · **Time:** <time> · **Verdict:** <verdict>`. For every decision you post as a PR comment, also run `python -m omi note <ID> --step <step> --verdict <verdict> "<text>"` so it shows under Reports on the board. If posting fails, warn and continue; the task file still has the report.
7. Advance runs `python -m omi clean <ID>` after merging and pulling, then the configured `host_test` from `.omi/config.json` on `development`. A failed post-merge test exits non-zero loudly; no automatic revert. An empty host_test is explicitly reported as skipped. Only when no other task is in progress, run the full clean: `python -m omi clean --all` if `python -m omi status` shows no planned task left (also removes the cached worker image), otherwise `python -m omi clean` (keeps the image as cache); it refuses with `RUNNING:` while any worker runs.
8. Report to the PO in at most 10 lines (with the tool/model/effort used), then continue with the next planned task from `python -m omi status` (same tool rules, step 0). Stop only on a PO decision (AGENTS.md `The PO decides`), a `QUOTA:` exit, or no planned task.

## Task-start tool choice
The Coordinator picks tool, concrete model and effort itself from the quota rules and `.omi/agents/CATALOG.md` (`## Models`, generated from `.omi/config.json` `model_notes`), resolving concrete IDs from `models` and `codex_models`. Spread tasks evenly across Claude Code and Codex, based on the task and available quota. Spread engineer and reviewer work across Claude and Codex; the architect (`omi-agent-architect`) is Claude only: `omi run` refuses it on Codex and never falls back to Codex on a usage limit. Record `tool`, model alias and explicit `effort` in the task before starting and state them in the report; no PO question, including for next tasks and resumes.
When the PO names a tool, use it and choose model and effort the same way. Never use `codex-default` or an omitted effort; `none` is only an explicit Codex choice.
