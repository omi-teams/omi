---
name: omi-task
description: Run one OMI task end to end - worktree, engineer in the Docker worker, review, PR, CI, merge into development.
argument-hint: TASK-NNN
---
Task: $ARGUMENTS. If empty, take the `next` task from `python -m omi status`.
Several IDs (`omi-task <ID> <ID>`) only when the PO asks: run `python -m omi parallel <IDs>` first and stop with its output on a conflict; then run each task's steps, engineers with `run_in_background`, no PO accept question per task.

The main checkout stays on `development`. `<wt>` is `../<repo-name>.wt/<ID>`.

0. Before starting or resuming, follow the task-start tool choice below and record the tool, model alias and effort; no PO question.
1. Check that every `depends` task is done and that the task's `role` (a file in `.omi/agents`) and `skills` (chosen from `.omi/skills/CATALOG.md`, regenerate with `python -m omi skills`) pass `python -m omi skills check <task-file>` (role default skills count too). Set `status: in-progress`, then commit on `development`. With a remote, push `development` right away (`git push`), so the squash merge of the PR does not conflict with an unpushed local commit.
2. If `<wt>` already exists, this is a resume (also in a new Claude Code or Codex session; Codex: follow this file for the ID): read its Checkpoint and `## Reports` and verify it with `git -C <wt> status` and `git -C <wt> log development..HEAD`. Otherwise run `git worktree add <wt> -b task/<ID> development`.
   Drive the task through its `workflow:` (none set: pick the lightest fitting one from `.omi/workflows/CATALOG.md` and write it; default `omi-flow-feature`) with `python -m omi step <ID> next` before and `done` after each step (it commits the task file itself; `WARN: scope touches ...` suggests `omi-flow-feature-sensitive`); `omi run` loads the current step's skills. `coordinator` steps are yours; an `auto` gate (accept after review PASS) needs no approval, `done` records `Auto accept: review PASS`; before `done` on a `po` gate, run `python -m omi step <ID> approve --why "<PO's words>"` to record the approval in `## Steps`.
3. Run the engineer in the Docker worker (never spawn an `omi-agent-engineer` subagent, never run it on the host):
   `python -m omi run <role> <ID> [--model M --effort E]` (role from the task, default `omi-agent-engineer`; add `--tool codex|claude` to override the `tool:` of task or role; when an agent hits its usage limit `omi run` switches to the other tool itself and records it in `## Checkpoint`, exit 5 with a `QUOTA:` line means both are out: tell the PO and stop, nothing is lost). Pass `--model/--effort` only when the AGENTS.md quota rules differ from `.omi/agents/<role>.md`. It prints the engineer's report.
   On a fix round `omi run` resumes the engineer's previous CLI session (same tool; `Session: <tool> <id> <role>` under `## Checkpoint`, transcripts in a per-task Docker volume, never on the host, removed by `omi clean`; a token found in it drops the session) with a short prompt pointing at the new findings; `--fresh` starts a new session, a tool switch starts fresh, a lost session prints `RESUME FAILED:` and starts fresh; read roles never resume. If the `post-run` hook fails, the engineer is resumed once with the hook's output tail to fix it and the hook reruns. So write fix-round findings under `## Checkpoint` and keep that `Session:` line.
   If it stops because Docker is not running or no token is found, tell the PO (token: `python -m omi token set`) and stop. There is no host fallback.
4. Check the diff before committing: `git -C <wt> status` and `git -C <wt> diff`. `omi run` prints `OUT OF SCOPE: <path>` (exit 3) for changes outside `scope`. Refuse those, and always refuse changes to `.gitattributes`, `.gitmodules` or any `.git*` path unless the scope names it exactly (no globs, e.g. `.github/workflows/ci.yml`): `git -C <wt> checkout -- <path>` or delete the new file. Then `git -C <wt> add -A` and commit on the host with the engineer's suggested conventional message.
5. Handle the engineer's result:
   - `DONE`: run `python -m omi run omi-agent-reviewer <ID>` (fresh instance in a read-only container; it first runs tests, scope and skills checks and, if one fails, reports it instead of starting: treat that as a fix round; skip it only by the path rule in AGENTS.md "Quota rules").
   - Review `FAIL`: run `python -m omi step <ID> back`, write the findings under `## Checkpoint` in `<wt>`'s task file after a line `Review round <N> FAIL:`, commit, and run step 3 again. After 2 failed fix rounds, ask the PO.
   - `NEEDS SCOPE`: if it fits the task goal, widen `scope` in the task file on `development` and commit it there (`omi run` copies the new scope into the worktree copy, `SCOPE SYNCED:`), and rerun. Otherwise ask the PO.
   - `FOUND: <one line>` (from any report, review or your own check): before any other step, file every finding about omi itself with `omi improve "<one line>" --kind bug --from <project>` (`--kind security` for security, `--kind idea` for ideas), setting `OMI_TASK=<source-task>` and `OMI_AGENT=<reporting-agent>` so provenance is preserved. With no omi project registered, retain the printed issue text and command for the user to run. Project bugs stay in the project: write a new task file for it (bugfix workflow; `omi-flow-feature-sensitive` for a security hole), commit it on `development` and push (`git push` with a remote). No PO question; run it after the current task (step 8).
6. On PASS, tick (`- [x]`) each criterion the reviewer marked ✓, for each `HOST` item the reviewer reported, run that check on the host, write `Host: <command> -> <result>` under `## Checkpoint` in `<wt>`'s task file and tick the criterion only on a pass (a failed host check is a fix round, step 5); no merge without one `Host:` line per `HOST` item. Set `status: done` in `<wt>`'s task file and commit. Then run `python -m omi hook pre-merge <ID>` (no hook file: no-op); a non-zero exit blocks the merge: treat it as a fix round (step 5). Then:
   - With a GitHub remote: `git -C <wt> push -u origin task/<ID>`, then write the body to a file. If the draft PR from the first build commit exists, run `gh pr edit task/<ID> --title "<title>" --body-file <file>`; only when no PR exists yet run `gh pr create --base development --head task/<ID> --title "<title>" --body-file <file>` (never `--fill`). Then `gh pr checks --watch`. If CI fails after accept, run `python -m omi step <ID> reopen --why "<CI failure reason>"`, record the findings in the Checkpoint and commit, then repeat from step 3 through review and accept again; it counts as a fix round (after 2 failed fix rounds, ask the PO). When green, run `gh pr merge --squash --delete-branch --subject "<title>"` (the PR title stays the squash commit subject), then `git pull`.
   - Without a remote: `git merge --squash task/<ID>`, then commit with the same `<title>`.
   - Title: `[TASK-NNN] <type>(<area>): <summary>`; type is one of feat, fix, docs, chore, refactor, test, ci; English, imperative, at most 72 characters.
   - Body sections, in order: `## Summary` (1-2 lines, plan and task id), `## Changes` (per file or area), `## Not in this PR`, `## Verification` (test command -> result, review rounds and verdicts, security review when the workflow has one, one `Host:` line per HOST check), `## Known issues` (or `none`).
   - PR comments: open the PR as a draft right after the first build commit is pushed (`gh pr create --draft --base development --head task/<ID> --title "<title>" --body-file <file>`, the Verification section is filled in at step 6); mark it ready (`gh pr ready`) once every review-type step of the workflow (review, security, any other `gate review`) has passed; a later FAIL or `step back` turns it back into a draft (`gh pr ready --undo`). While a PR for `task/<ID>` exists, `omi run` posts each final report and hook result as a comment itself. You post Coordinator decisions (scope widened, step back, fix round, `Host:` checks) and PO approvals (quote the PO's words) by writing the header and text to a file and running `gh pr comment task/<ID> --body-file <file>` (never `--body` with `\n`); the header is `**Step:** <step> · **Agent:** Coordinator · **Time:** <time> · **Verdict:** <verdict>`. For every decision you post as a PR comment, also run `python -m omi note <ID> --step <step> --verdict <verdict> "<text>"` so it shows under Reports on the board. If posting fails, warn and continue; the task file still has the report.
7. Post-merge check: run the project's test command on `development`. Then remove `<wt>` and `task/<ID>` if still present (`gh pr merge --delete-branch` already does both), and clean up: if `python -m omi status` shows no planned task left, run `python -m omi clean --all` (also removes the cached worker image); otherwise run `python -m omi clean` and keep the image as cache for the next task.
8. Report to the PO in at most 10 lines (with the tool/model/effort used), then continue with the next planned task from `python -m omi status` (same tool rules, step 0). Stop only on a PO decision (AGENTS.md `The PO decides`), a `QUOTA:` exit, or no planned task.

## Task-start tool choice
The Coordinator picks tool, concrete model and effort itself from the quota rules and `.omi/agents/CATALOG.md` (`## Models`, generated from `.omi/config.json` `model_notes`), resolving concrete IDs from `models` and `codex_models`. Spread tasks evenly across Claude Code and Codex, based on the task and available quota. Record `tool`, model alias and explicit `effort` in the task before starting and state them in the report; no PO question, including for next tasks and resumes.
When the PO names a tool, use it and choose model and effort the same way. Never use `codex-default` or an omitted effort; `none` is only an explicit Codex choice.
